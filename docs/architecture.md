# 架构方案

## 1. 分层

| 层 | 职责 | 技术 |
|---|---|---|
| 表现层 | 编辑器、目录树、状态栏 | React 19 + TypeScript + Vite |
| 编辑器 | 所见即所得，Markdown 为磁盘格式 | Milkdown（remark + ProseMirror） |
| 桥接层 | 类型化 command 封装，无业务逻辑 | `@tauri-apps/api` |
| 核心层 | 文件读写、解析、统计、索引 | Rust |
| 存储 | Vault 目录（唯一真相源）+ 可重建索引 | 文件系统 |

前端**不持有任意路径的读写权限**。所有文件操作经自定义 command，路径在 Rust 侧
`canonicalize` 后校验必须位于 vault 根目录之内，防止路径穿越。

## 2. 三条工程约束

### 2.1 中文检索不引入 tantivy / FTS5

SQLite FTS5 的 `unicode61` 分词器不切分中文，要可用必须挂 jieba 做自定义 tokenizer；
tantivy 同理。个人稿库上限通常为千万字以内，Rust 侧字符二元组倒排索引足够，
零外部依赖、零词典。

**查询流程**：二元组交集缩小候选 → 子串校验 → 按命中次数排序。

第二步不可省略。二元组只保证「这两个字都出现过」，不保证相邻 ——
查「风在」时，`风过了，字还在` 的两个二元组（`风过`、`过，`…）里并不含 `风在`，
但候选集是按「包含 `风` 开头的二元组」和「包含 `在` 结尾的二元组」求交得到的，
所以必须再用子串校验把不相邻的假阳性剔掉。

**规模实测**（debug 构建，1000 章 / 48 万字）：建索引 101ms，检索 15ms。
release 构建会显著更快。基准测试标了 `#[ignore]`，不进 CI：

```bash
cargo test --lib 千章规模 -- --ignored --nocapture
```

**索引与磁盘的关系**：索引是纯内存的派生结构，随扫描全量重建、随保存增量更新
（`upsert` 按旧正文重算二元组把该文档从倒排里摘掉再重新插入）。
应用重启即重建，不做持久化 —— 与「文件即真相」一致。

**front matter 不进索引**：只索引正文，否则搜「楔子」会被每章标题误命中。

### 2.2 自动保存 = 原子写 + 防抖 + 冲突检测

```
write <file>.tmp → fsync → rename
```

保证任何时刻崩溃都不留半截文件。写入前比对磁盘 mtime，不一致则提示
「文件已被外部修改」，不静默覆盖。中文输入法 composition 期间不触发保存与统计，
否则会写入拼音中间态。

### 2.3 崩溃恢复日志

自动保存有 800ms 防抖，强杀进程或 WebView 崩溃会丢掉窗口内的输入。补偿手段是
一份短命的本地日志：

| 层 | 时机 | 存放 | 丢失窗口 |
|---|---|---|---|
| 恢复日志 | 停止输入 150ms | `localStorage` | ~150ms |
| 正式落盘 | 停止输入 800ms | Markdown 文件 | — |

日志的写入间隔刻意远短于自动保存：写 localStorage 的代价远低于落盘，值得用更密的
节奏换更小的窗口。成功落盘后立即清除——日志只做短期兜底，不是归档数据。

启动时若发现残留日志，只有**内容与磁盘不同**才提示恢复，否则说明那次改动其实已经
落盘，静默清掉。恢复的动作是「直接把日志内容写盘，再重建编辑器」，不走
「标记脏 → 等自动保存」，因为重建编辑器会触发序列化基线回填，那条路径上容易把
待保存状态抹掉。

换库时丢弃上一个库的日志：日志里存的是相对路径，跨库沿用可能把 A 库的内容写进
B 库的同名章节。

### 2.4 版本快照不用 git 全量

按章做内容寻址（sha256 → blob），manifest 记录快照点，天然去重。
git 作为可选导出而非核心依赖。

## 3. 所见即所得的保真风险

Markdown 是磁盘格式，ProseMirror 是内存格式，中间有一次有损转换。中文排版恰好
踩在这条链路最脆弱的位置：

| 风险 | 表现 | 对策 |
|---|---|---|
| 软换行 | 段内 Shift+Enter 折行丢失 | 序列化固定写行尾反斜杠 |
| 全角标点 | `……` `——` `「」` 被转义或规范化 | 关掉 remark 的字符串转义，白名单放行 |
| front matter | YAML 头进文档树被当分隔线吃掉 | 解析前剥离，序列化后原样拼回 |
| 段首缩进 | 手动打的全角空格被折叠 | 存储层不写缩进字符，靠 CSS `text-indent: 2em` |

**护栏**：doc 未改动则完全跳过写盘；序列化结果与原文字节比对，不一致即告警而非静默覆盖。
P0 的验收标准之一是「打开任意稿件 → 不做编辑 → 关闭，`git diff` 为空」。

### 3.1 软换行的处置（已决策）

不为软换行做自定义序列化规则。理由：

- 中文小说的对话分行靠**换段**实现，不靠段内折行；段内折行属于诗歌、歌词等少数场景；
- remark 会把行尾双空格规范化成反斜杠（`\`），这是一次性的表示形式统一，**内容不丢**；
- 规范化之后结果稳定，二次序列化不再变化。

该行为由 `src/lib/markdown.test.ts` 的「段内折行内容不丢，只是表示形式统一」固化。
若将来要支持诗歌排版，需要为 `break` 节点单独写序列化规则并补测试。

## 4. 数据模型

每章 front matter：

```yaml
id: 01JCV...        # ULID，重命名文件不变
title: 楔子
order: 1
status: draft       # draft | revising | done
characters: [沈砚, 阿箬]
pov: 沈砚
words: 3214         # 派生值，可重建，仅作快速展示
```

`words` 落盘是刻意设计：让目录树不必打开每个文件就能显示字数。它是缓存，
重建索引时全量刷新，允许短暂不准。未知字段通过 `serde(flatten)` 保留，不丢用户自定义键。

### 4.1 `order` 与文件名前缀

`order` 字段与文件名前缀（`001-`）是同一信息的两处表达，**以 `order` 为准**。
重排时按新位置重编号并同步修正前缀，否则在文件管理器里看到的顺序会和应用内不一致。

重排只改写序号或文件名真正变化的文件：按位置重编号时，未换位的章节序号本就不变，
因此一次上移/下移通常只动两个文件，不会让整卷产生无谓的 git diff。
这同时顺带修掉序号空洞与重复（`1,7,9` → `1,2,3`）。

改名走两阶段（先挪到临时名腾空目标位，再落位），避免两章互换文件名时互相占用。
同名章节通过追加 `-2` 后缀区分，不会互相覆盖。

## 5. 字数统计口径

`total = CJK 字符数 + 非 CJK 单词数`，与 Word「中文字数」对齐，偏差要求 ≤ 1%。
标点默认不计入，口径可在 `_vault.yaml` 配置。CJK 判定覆盖：

- U+4E00–U+9FFF 基本区
- U+3400–U+4DBF 扩展 A
- U+F900–U+FAFF 兼容区
- U+3040–U+30FF 假名
- U+AC00–U+D7AF 谚文

## 7. 后续风险

- **docx 导出**：中文排版（首行缩进 2 字符、宋体小四、1.5 倍行距）必须用 `docx-rs`
  精确控制，不走 HTML→docx 转换，那条路对中文缩进的处理不可靠。
- **Windows 路径**：统一用 `PathBuf` 而非 `String` 拼接，避免中文路径与长路径问题。
- **Milkdown 版本**：preset 包之间耦合紧，必须锁定版本，升级需同步验证。
- **serde_yaml 已归档**：当前用 0.9.34 稳定版，后续若需维护可迁 `serde_yml` 或 `yaml-rust2`。
