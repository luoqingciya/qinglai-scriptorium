# 架构方案

## 1. 分层

| 层 | 职责 | 技术 |
|---|---|---|
| 表现层 | 编辑器、目录树、状态栏 | React 19 + TypeScript + Vite |
| 编辑器 | 所见即所得，Markdown 为磁盘格式 | Milkdown（remark + ProseMirror） |
| 桥接层 | 类型化 command 封装，无业务逻辑 | `@tauri-apps/api` |
| 核心层 | 文件读写、解析、统计、索引 | Rust |
| 存储 | Vault 目录（唯一真相源）+ 可重建索引 | 文件系统 |

前端**不持有任意路径的读写权限**。所有文件操作经自定义 command，路径在 Rust 侧
`canonicalize` 后校验必须位于 vault 根目录之内，防止路径穿越。

## 2. 三条工程约束

### 2.1 中文检索不引入 tantivy / FTS5

SQLite FTS5 的 `unicode61` 分词器不切分中文，要可用必须挂 jieba 做自定义 tokenizer；
tantivy 同理。个人稿库上限通常为千万字以内，Rust 侧字符二元组倒排索引足够，
零外部依赖、零词典。

**查询流程**：二元组交集缩小候选 → 子串校验 → 按命中次数排序。

第二步不可省略。二元组只保证「这两个字都出现过」，不保证相邻 ——
查「风在」时，`风过了，字还在` 的两个二元组（`风过`、`过，`…）里并不含 `风在`，
但候选集是按「包含 `风` 开头的二元组」和「包含 `在` 结尾的二元组」求交得到的，
所以必须再用子串校验把不相邻的假阳性剔掉。

**规模实测**（debug 构建，1000 章 / 48 万字）：建索引 101ms，检索 15ms。
release 构建会显著更快。基准测试标了 `#[ignore]`，不进 CI：

```bash
cargo test --lib 千章规模 -- --ignored --nocapture
```

**索引与磁盘的关系**：索引是纯内存的派生结构，随扫描全量重建、随保存增量更新
（`upsert` 按旧正文重算二元组把该文档从倒排里摘掉再重新插入）。
应用重启即重建，不做持久化 —— 与「文件即真相」一致。

**front matter 不进索引**：只索引正文，否则搜「楔子」会被每章标题误命中。

### 2.2 自动保存 = 原子写 + 防抖 + 冲突检测

```
write <file>.tmp → fsync → rename
```

保证任何时刻崩溃都不留半截文件。写入前比对磁盘 mtime，不一致则提示
「文件已被外部修改」，不静默覆盖。中文输入法 composition 期间不触发保存与统计，
否则会写入拼音中间态。

### 2.3 崩溃恢复日志

自动保存有 800ms 防抖，强杀进程或 WebView 崩溃会丢掉窗口内的输入。补偿手段是
一份短命的本地日志：

| 层 | 时机 | 存放 | 丢失窗口 |
|---|---|---|---|
| 恢复日志 | 停止输入 150ms | `localStorage` | ~150ms |
| 正式落盘 | 停止输入 800ms | Markdown 文件 | — |

日志的写入间隔刻意远短于自动保存：写 localStorage 的代价远低于落盘，值得用更密的
节奏换更小的窗口。成功落盘后立即清除——日志只做短期兜底，不是归档数据。

启动时若发现残留日志，只有**内容与磁盘不同**才提示恢复，否则说明那次改动其实已经
落盘，静默清掉。恢复的动作是「直接把日志内容写盘，再重建编辑器」，不走
「标记脏 → 等自动保存」，因为重建编辑器会触发序列化基线回填，那条路径上容易把
待保存状态抹掉。

换库时丢弃上一个库的日志：日志里存的是相对路径，跨库沿用可能把 A 库的内容写进
B 库的同名章节。

### 2.4 版本快照不用 git 全量

按章做内容寻址（sha256 → blob），manifest 记录快照点，天然去重。
git 作为可选导出而非核心依赖。

### 2.5 界面验证走 CDP，不看进程存活

**这一条是踩坑换来的。**

Tauri 的 debug 构建加载 `devUrl`（`http://localhost:1420`），只有 release 才用
`frontendDist`。直接 `cargo build` 后运行 `target/debug/*.exe`，WebView 会去连一个
没启动的 Vite，得到「无法访问此页面」的错误页——**而进程照样存活**。

于是「检查进程存在」这个验证手段会稳定地给出假阳性。截屏又被安全策略拦住
（`Add-Type` 加载 .NET 被禁），一度以为 GUI 无法自动验证。

真正的办法是走 WebView2 的远程调试端口：

```bash
WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS="--remote-debugging-port=9222" pnpm tauri dev
node scripts/ui-check.mjs --vault <稿库路径>
```

`scripts/ui-check.mjs` 通过 CDP 读 DOM，断言：不是连接错误页、`.app` 已挂载、
编辑器有正文、无 console 报错。带 `--vault` 时还会预置稿库并检查章节数与编辑器内容。

这比截图更可靠：截图只能人眼看，CDP 能给出可断言的布尔值。

## 3. 所见即所得的保真风险

Markdown 是磁盘格式，ProseMirror 是内存格式，中间有一次有损转换。中文排版恰好
踩在这条链路最脆弱的位置：

| 风险 | 表现 | 对策 |
|---|---|---|
| 软换行 | 段内 Shift+Enter 折行丢失 | 序列化固定写行尾反斜杠 |
| 全角标点 | `……` `——` `「」` 被转义或规范化 | 关掉 remark 的字符串转义，白名单放行 |
| front matter | YAML 头进文档树被当分隔线吃掉 | 解析前剥离，序列化后原样拼回 |
| 段首缩进 | 手动打的全角空格被折叠 | 存储层不写缩进字符，靠 CSS `text-indent: 2em` |

**护栏**：doc 未改动则完全跳过写盘；序列化结果与原文字节比对，不一致即告警而非静默覆盖。
P0 的验收标准之一是「打开任意稿件 → 不做编辑 → 关闭，`git diff` 为空」。

### 3.1 软换行的处置（已决策）

不为软换行做自定义序列化规则。理由：

- 中文小说的对话分行靠**换段**实现，不靠段内折行；段内折行属于诗歌、歌词等少数场景；
- remark 会把行尾双空格规范化成反斜杠（`\`），这是一次性的表示形式统一，**内容不丢**；
- 规范化之后结果稳定，二次序列化不再变化。

该行为由 `src/lib/markdown.test.ts` 的「段内折行内容不丢，只是表示形式统一」固化。
若将来要支持诗歌排版，需要为 `break` 节点单独写序列化规则并补测试。

## 4. 数据模型

每章 front matter：

```yaml
id: 01JCV...        # ULID，重命名文件不变
title: 楔子
order: 1
status: draft       # draft | revising | done
characters: [沈砚, 阿箬]
pov: 沈砚
words: 3214         # 派生值，可重建，仅作快速展示
```

`words` 落盘是刻意设计：让目录树不必打开每个文件就能显示字数。它是缓存，
重建索引时全量刷新，允许短暂不准。未知字段通过 `serde(flatten)` 保留，不丢用户自定义键。

### 4.1 `order` 与文件名前缀

`order` 字段与文件名前缀（`001-`）是同一信息的两处表达，**以 `order` 为准**。
重排时按新位置重编号并同步修正前缀，否则在文件管理器里看到的顺序会和应用内不一致。

重排只改写序号或文件名真正变化的文件：按位置重编号时，未换位的章节序号本就不变，
因此一次上移/下移通常只动两个文件，不会让整卷产生无谓的 git diff。
这同时顺带修掉序号空洞与重复（`1,7,9` → `1,2,3`）。

改名走两阶段（先挪到临时名腾空目标位，再落位），避免两章互换文件名时互相占用。
同名章节通过追加 `-2` 后缀区分，不会互相覆盖。

## 5. `[[双链]]` 与反链

语法：`[[目标标题]]`，可选别名 `[[目标标题|显示文字]]`，可选锚点 `[[目标标题#小节]]`
（锚点当前只被忽略，不做跳转定位）。

### 5.1 按标题匹配，不引入 ID

`[[楔子]]` 是作者自然会写的形式，`[[01JCV...]]` 不是。代价是重命名后旧引用变成
**悬空链接**——这由 `dangling()` 显式暴露，让用户自己决定改不改，
而不是在重命名时静默批量替换（那样会误伤同名的不同章节）。

解析规则（Rust `links::extract` 与前端 `findWikilinks` 必须一致）：

| 规则 | 原因 |
|---|---|
| 不跨行 | `[[` 与 `]]` 相隔一整段，几乎一定是误输入 |
| 空目标忽略 | `[[]]`、`[[  ]]` 不是链接 |
| 去 `#` 之后的部分 | 锚点暂不支持定位 |
| 首尾空白与大小写规范化 | 建表查表必须走同一函数，否则永远匹配不上 |
| front matter 不进索引 | 元数据里的 `[[...]]` 是普通字符串 |

### 5.2 索引是派生的，不落盘

`LinkIndex` 与检索索引同构：随扫描重建、随保存 `upsert`（按旧正文摘边再插边）、
随删除 `forget`。稿件正文里只有 `[[标题]]` 这几个字符，没有 ID、没有私有格式。

反链面板默认收起。写作时宽度是稀缺资源，反链是「偶尔查一下」的信息。

### 5.3 编辑器内高亮用 Decoration，不用自定义 node

**这是本节最重要的决策。**

自定义 node/mark 需要同时写 schema、parser、serializer 三处规则，任何一处偏差
都会让 Markdown 往返失真——这是本项目最不能接受的风险（见 §3）。

Decoration 只是在已有文本上叠一层视觉样式，**不改变文档结构**，
因此 `getMarkdown()` 的输出与没有这个插件时完全一致。代价是 `[[...]]` 在文档里
始终是纯文本，用户不能用光标「选中一个链接节点」；但对写作场景来说这不重要，
作者要的是看见并点得动。

点击走事件委托：装饰层生成带 `data-wikilink` 的 `<span>`，
在容器上监听 click 后用 `closest` 取目标，比给每个 span 绑监听省。

### 5.4 已知边界

- 同名章节只解析到第一条（`resolve` 用 `find`），不做消歧
- 悬空链接只在索引层检测，暂不在编辑器里标红
- 重命名不自动改写引用，只让旧引用变悬空
- 锚点不做定位跳转

## 6. 导出 docx

### 6.1 不走 HTML → docx

那条路对中文缩进的处理不可靠：HTML 的 `text-indent: 2em` 落到 OOXML 时常被转成
固定 twips 值，换个字号就错位。Word 有专门的字符单位缩进，但转换器不用它。

所以用 `docx-rs` 直接构造 OOXML，段落属性、字体槽、行距全部显式指定。

### 6.2 排版参数

对齐国内长篇小说通行格式，全部可在 `ExportOptions` 里覆盖：

| 项 | 默认值 | 说明 |
|---|---|---|
| 字体 | `SimSun` | 同时写入 ascii / hAnsi / **eastAsia** 三个槽位 |
| 字号 | 24（半磅） | 12pt 小四 |
| 行距 | 360 | 240 = 单倍，360 = 1.5 倍 |
| 首行缩进 | 200（1/100 字符） | 2 字符 |
| 章间分页 | 开 | `pageBreakBefore` |

字体名写 `SimSun` 而非「宋体」—— 后者在英文版 Word 里找不到。
`eastAsia` 槽位是中文正确显示的前提，只设 `ascii` 不够。

### 6.3 docx-rs 0.4.22 的两个坑

**坑一：`Paragraph::first_line_chars()` 是死代码。**

`BuildXML for Indent` 只读 `special_indent` 字段，`first_line_chars` 只参与
JSON 序列化，写 XML 时被完全忽略。调用它静默无效，不报错。

必须绕开：

```rust
let twips = font_size_half_pt * 10 * first_line_chars / 100; // 1pt = 20 twips
para.indent(None, Some(SpecialIndentType::FirstLine(twips)), None, None)
```

按字号换算而非写死 480，换字号时缩进才跟着走。

**坑二：方法名是 `hi_ansi` 不是 `h_ansi`。**

写错只会得到编译错误，还算好。真正麻烦的是坑一——它编译通过、运行不报错、
导出「成功」，只是缩进没生效。

### 6.4 双链必须在解析前剥离

`strip_wikilinks` 要在交给 pulldown-cmark **之前**对整段正文执行。

不能在解析后按 `Event::Text` 处理：pulldown-cmark 会把 `[[` 和 `]]` 当成可能的
链接语法拆成独立事件，那时再拼就看不到完整的 `[[目标]]` 了 ——
实测会输出成 `[` `[` `夜航` `]` `]` 五个 run。

### 6.5 导出目标路径不受 `safe_join` 约束

导出目标通常落在稿库之外（桌面、投稿目录）。路径来自系统保存对话框，
是用户显式选择的结果。

仍保留两条底线校验：必须是 `.docx` 后缀、父目录必须已存在。
即使用户手输路径打错，也只会得到明确报错，不会在意外位置生成文件。

### 6.6 已知边界

- 图片、表格不导出（跳过，不报错）
- 有序列表不自动编号，统一用 `1.` 前缀（`pulldown-cmark` 的起始号可用但未接）
- 不做目录页、页眉页脚、页码
- 只导出全库，不支持按卷/选中章节导出

## 7. 字数统计口径

`total = CJK 字符数 + 非 CJK 单词数`，与 Word「中文字数」对齐，偏差要求 ≤ 1%。
标点默认不计入，口径可在 `_vault.yaml` 配置。CJK 判定覆盖：

- U+4E00–U+9FFF 基本区
- U+3400–U+4DBF 扩展 A
- U+F900–U+FAFF 兼容区
- U+3040–U+30FF 假名
- U+AC00–U+D7AF 谚文

## 8. 写作统计

### 8.1 这是「索引不落盘」的唯一例外

检索索引、双链索引都能从当前文件全量重建，所以纯内存。但**每日字数**是时间序列——
当前稿件里没有「昨天有多少字」这个信息，不记录就永久丢失。

因此统计必须持久化，落在稿库内的 `.qinglai/stats.json`：

- 属于稿库的一部分，换机器打开同一稿库能看到同样的曲线；
- 隐藏目录，扫描时被跳过，不会混进章节列表；
- **丢了不影响任何稿件**，最坏情况是趋势图从头开始。

这是原则的例外，不是原则的松动：判断标准是「能否从文件重建」。能重建的就不落盘，
不能重建的才落盘，且必须放在不影响稿件的位置。

### 8.2 存总量，不存增量

每日记录**最后一次**的全库总字数，而不是「当日新增」。

因为删改会让字数下降。若累加增量，一次大删会让后续所有天数为负，反而失真。
存总量、由相邻两日求差，才是作者真正关心的「这本书写到多少字了」。

### 8.3 只返回有记录的日子

趋势图不补零。没写作的那天不画柱子——补零会让「停更一周」看起来像
「写了一周空白」，视觉上反而更误导。

差值也按**相邻记录点**算，跨过空白日。11-01 记 1000、11-03 记 1800，
则 11-03 的增量是 800，不是 0。

### 8.4 写入节流 60 秒

统计只关心当日最后一次，不必每次保存都写文件。60 秒粒度足够，
又能避免一分钟内敲几百次保存就写几百次 JSON。

失败时不重置节流时间戳：统计是附加信息，不该因为一次写盘失败就在接下来的
每次保存里反复重试。

### 8.5 保存后必须同步章节字数

`flush` 成功后要更新 snapshot 里该章的 `words` 并重算 `totalWords`。

不更新的话，记录进统计的永远是「打开稿库时」的旧值——趋势会变成一条平线，
而用户完全看不出异常。这条有专门的测试锁住。

### 8.6 已知边界

- 只在保存后记录，纯阅读不产生数据点
- 不区分「今天写了哪些章」，只有全库总量
- 保留 730 天，超出后丢弃最老记录
- 时间用本地时区（作者认知的「今天」是墙上时钟）

## 9. 人物卡

### 9.1 数据本来就在稿件里

不需要额外的「角色文件」。每章的 front matter 已经写着：

```yaml
characters: [沈砚, 阿箬]
pov: 沈砚
```

人物索引只是把它倒过来排一遍：角色名 → 出场章节。与检索、双链一样是纯内存的
派生结构，随扫描重建、随保存 `upsert`、随删除 `forget`。

**这比「单独维护角色库」更适合小说写作**：作者在写某一章时顺手记下谁在场，
不会额外增加一份需要同步维护的数据。角色设定可以放在 `设定/人物/沈砚.md` 里，
那是普通章节，走的是双链而不是人物索引。

### 9.2 视角人物自动算作出场

作者写 `pov: 阿箬` 却忘了在 `characters` 里列一遍，是很容易发生的事。
索引在聚合时会把 `pov` 并入 `characters`，并对该章标记 `isPov`。

这不是猜测，是定义使然：视角人物就是这一章的叙述者，不可能不在场。

去重也要做：`characters: [阿箬]` + `pov: 阿箬` 只算一次出场，`povCount` 也只加一。

### 9.3 一次返回全部

角色通常几十个、每个出场几章，整份数据不到 100KB。一次拿全比按需二次请求简单，
点击角色能立即展开，没有等待。

### 9.4 已知边界

- 同名不同人无法区分（按名字精确匹配）
- 只认 front matter，正文里提到的名字不计入（那需要实体识别，不做）
- 出场顺序按文件路径排，不是按剧情时间线
- 不做角色关系图

## 10. 阶段规划

| 阶段 | 内容 | 完成标志 |
|---|---|---|
| P0 骨架 | vault 扫描、三栏、编辑、原子保存、字数 | 连续写 2 小时不丢字 |

### 10.1 主题与专注模式（P1d）

**三套主题**：暗色（默认）、亮色、护眼（米黄底 + 深褐字，模拟纸张阅读）。
通过 `:root[data-theme="..."]` 覆盖 CSS 变量实现，不重写样式表。
主题偏好持久化到 `localStorage`，在模块加载时立刻应用到 DOM 以避免 FOUC。

**专注模式**：F11 切换，隐藏目录树，编辑区铺满全宽并给更大的 max-width（42rem → 56rem）。
状态持久化到 `localStorage`。状态栏提供按钮入口。

两者都是纯前端状态，不涉及 Rust 侧。

## 11. 后续风险

- **docx 导出**：中文排版（首行缩进 2 字符、宋体小四、1.5 倍行距）必须用 `docx-rs`
  精确控制，不走 HTML→docx 转换，那条路对中文缩进的处理不可靠。
- **Windows 路径**：统一用 `PathBuf` 而非 `String` 拼接，避免中文路径与长路径问题。
- **Milkdown 版本**：preset 包之间耦合紧，必须锁定版本，升级需同步验证。
- **serde_yaml 已归档**：当前用 0.9.34 稳定版，后续若需维护可迁 `serde_yml` 或 `yaml-rust2`。
